09-12-26 12:01 1.3, 6.6, 9, 12.2 Decision The shape tools' shared drawing behaviour implementation, 09-12-26 (docs/Basic-Shape-Shared-Drawing-Implementation.md, Section 2). 12.2, decision 4 (option B): every drawing tool that reads Alt for "draw from center" also reads Ctrl for it, and Alt keeps the meaning this table gives it. The reason is a desktop limitation, not a preference: Cinnamon's window manager takes Alt plus a mouse button as its own window-move gesture (org.cinnamon.desktop.wm.preferences mouse-button-modifier reads <Alt>, verified 09-12-26 and twice before), so an Alt+drag never reaches the canvas there and the centre-draw behaviour does not exist for that user by any change to the tool. The Basic Shape PRD's 2.3 reserves Ctrl "for future use, such as snapping to item edges" and nothing reads it during a drag today — no shape tool reads ControlModifier, the canvas view reads it only on the wheel for zoom, and the Text tool reads it for its editor shortcuts — so the edge snapping it is reserved for will need another key or a chord when it is built. The 12.2 row for Ctrl while drawing, "special modifier per tool", is read with this second route added; the Ctrl+drag skew of that row's example is a transform-handle gesture of the Select tool and is untouched. This work adds the second route in the drawing tools only; the Zoom tool's Alt+click (acceptance pass row 20) and the blur brush's Alt+paint eraser belong to other PRDs and stay without a working route on that desktop until their own follow-up. 1.3: the locked and hidden layer warning the Basic Shape PRD's 2.1 asks for is the never-disabled message, shown through check_requirements from one BaseTool helper; no control is disabled and nothing is greyed out. 6.6: the "Tool over locked layer item" cursor row names a locked item, not a locked layer, so it does not cover that press guard and no cursor change is built for it. Document Overview

Purpose

This document defines the user interface layout, behavior, and interaction patterns for SnapMock. It covers the main window structure, all panels and widgets, menu and toolbar organization, keyboard shortcuts, theming, context menus, dialogs, and accessibility requirements. This PRD is a companion to the Technical Architecture PRD and is intended to be consumed by Claude Code to produce a detailed implementation plan.

Scope

This document covers all UI chrome surrounding the canvas: window layout, panels, menus, toolbars, status bar, dialogs, and keyboard shortcuts. Individual annotation tool interaction behaviors (how the arrow tool works, how the text tool handles editing, etc.) are covered in separate per-tool PRDs. The canvas rendering behavior is covered in the Technical Architecture PRD.

UI Design Principles

  • Familiar and discoverable: follow established conventions from tools like Snagit, GIMP, and Figma. Users should feel at home immediately.
  • Canvas-first: maximize canvas real estate. All panels are dockable and collapsible. The canvas should occupy at least 60% of the window area in the default layout.
  • Non-modal workflow: avoid modal dialogs wherever possible. Use inline editing, dockable panels, and transient popups instead.
  • Keyboard-driven efficiency: every frequent operation has a keyboard shortcut. Power users should be able to work without touching the mouse for most operations.
  • Visual consistency: use a cohesive icon set, consistent spacing, and uniform control sizes across all panels and toolbars.
  • Responsive: the UI adapts gracefully from 1280x720 minimum resolution to ultrawide 5120x1440 displays.
  • Never-disabled controls: controls are never grayed out or disabled. If an action cannot be performed because its requirements are not met, clicking the control displays an informative message explaining exactly which requirements are unmet. This keeps the interface explorable and self-documenting at all times.

Canvas Area

Visual Layout

The canvas area occupies the central region of the main window. It consists of the SnapView (QGraphicsView) rendering the SnapScene. The canvas is surrounded by the pasteboard area that extends infinitely in all directions (users can pan beyond the canvas bounds). The pasteboard color is configurable (default: neutral gray #808080) to provide contrast against the canvas color.

Canvas Background

  • When no image is loaded, the canvas shows the canvas color (default: white) and a centered prompt: "Drag an image here, paste from clipboard (Ctrl+V), or go to File > Import Image" in gray text. The canvas color is the fill color of the working area and is included in exports behind any transparent content.
  • When an image is loaded as the background layer, it fills the canvas exactly.
  • Transparent areas are rendered as a checkerboard pattern (alternating light gray and white 8x8 pixel squares) to visually distinguish transparency from white.
  • The canvas boundary is indicated by a subtle 1px dark gray border and a drop shadow against the pasteboard.

Rulers

  • When enabled (View > Show Rulers), horizontal and vertical rulers are drawn along the top and left edges of the viewport.
  • Rulers show pixel measurements relative to the canvas origin (0,0 at top-left of canvas).
  • Ruler tick marks adapt to the zoom level: at low zoom, major ticks every 100px; at high zoom, major ticks every 10px or 1px.
  • The current cursor position is indicated on both rulers by a small triangular marker.
  • Ruler background: light gray (light theme) or dark gray (dark theme). Text: dark gray or light gray respectively.

Grid

  • When enabled (View > Show Grid), a grid overlay is drawn on the canvas.
  • Grid lines are rendered as 1px lines at 20% opacity (subtle enough to not distract).
  • Grid size matches the snap grid size (default 10px), configurable in Preferences.
  • At zoom levels below 200%, minor grid lines are hidden and only major grid lines (every 5 grid units) are shown to avoid visual clutter.

Guides

Guides are user-placed horizontal or vertical reference lines that span the full width or height of the canvas. They assist with aligning items across the composition. Guides are non-printing and are excluded from all exports.

  • Creating guides: Click and drag from the horizontal ruler to place a horizontal guide, or from the vertical ruler to place a vertical guide. A preview line follows the cursor during the drag. Release to place the guide at the current position.
  • Moving guides: Hover over a guide line until the cursor changes to a double-headed resize arrow. Click and drag to reposition. Shift+drag constrains movement to whole pixel values.
  • Deleting guides: Drag a guide back onto its originating ruler to remove it. Alternatively, use View > Clear All Guides to remove all guides at once.
  • Snapping: When View > Snap to Guides is enabled, item edges and centers snap to nearby guide lines during move, resize, and creation operations. The snap tolerance is the same as grid snap tolerance (configurable in Preferences, default 5px).
  • Locking: When View > Lock Guides is enabled, guides cannot be moved or deleted by mouse interaction. They can still be cleared via the Clear All Guides menu command.
  • Appearance: Guides render as 1px lines in the accent color (default: cyan #00BFFF) at 70% opacity. Guide color is configurable in Preferences. Guides render above the canvas content but below selection handles and tool overlays.
  • Persistence: Guide positions are saved with the project file (.smk) and restored when the project is reopened.

Implementation

  • Themes are implemented as Qt Style Sheets (QSS) stored in resources/themes/light.qss and resources/themes/dark.qss.
  • All colors are defined as named constants in the QSS files for easy customization.
  • Icons use SVG format and include both light and dark variants (or use a single SVG with CSS-controllable fill colors).
  • Theme switching is live (no restart required). Changing the theme re-applies the QSS and refreshes all widgets.
  • Canvas-specific rendering (selection handles, grid, ruler colors) reads theme values from a central ThemeManager class, not from QSS directly.

Accessibility

  • All interactive controls have accessible names and descriptions set via QAccessible or setAccessibleName()/setAccessibleDescription().
  • All toolbar buttons and menu items have text labels accessible to screen readers, even when only icons are visually displayed.
  • Tab order is logical: Menu Bar > Main Toolbar > Tool Options Bar > Left Tool Palette > Canvas > Layer Panel > Property Panel.
  • Focus indicators are visible: a 2px accent-colored outline around the focused control.
  • Color is not the only indicator of state: selected items have both a color change and a pattern (dashed outline). Locked layers show both a lock icon and reduced opacity.
  • All text meets WCAG 2.1 AA contrast ratio (4.5:1 for normal text, 3:1 for large text) in both light and dark themes.
  • Canvas zoom supports users with low vision. The pixel grid at high zoom aids precise work.
  • Status bar messages are announced to screen readers when they change.
  • All keyboard shortcuts are documented and accessible via the Help > Keyboard Shortcuts dialog.
  • In a future phase, support high-contrast mode for users who need it.

Responsive Behavior & Window Management

Minimum Window Size

The minimum window size is 1024x600 pixels. Below this, the window cannot be resized further. At this size, the Right Panel stack auto-collapses to icon-only mode (small icons for layer visibility/lock only) and the Tool Options Bar collapses into an overflow menu.

Panel Collapse Behavior

  • When the window width drops below 1280px, the Layer Panel and Property Panel automatically collapse to a narrow mode (200px) with abbreviated controls.
  • When the window width drops below 1024px, right panels collapse to icon-strip mode (48px) showing only layer thumbnails. Clicking a thumbnail opens a floating popover with full controls.
  • The Left Tool Palette always remains as a single column of icons (48px wide) and does not collapse further.
  • All collapse thresholds are configurable in Preferences.

Multi-Monitor Support

  • Floating panels (undocked QDockWidgets) can be moved to a second monitor.
  • The application remembers the monitor and position of floating panels across sessions.
  • If a saved panel position refers to a monitor that is no longer connected, the panel is moved to the primary monitor.

Session Persistence

The following UI state is saved and restored across application sessions via QSettings:

  • Window position, size, and maximized/fullscreen state.
  • Panel dock positions, sizes, and visibility states.
  • Active theme (Light/Dark/System).
  • Last-used export settings per format.
  • Recent file list.
  • Toolbar and panel visibility toggles.
  • Grid/snap/ruler toggle states.
  • Last-used tool and its option values.
  • Zoom level per recently opened project (stored in recent file metadata).
