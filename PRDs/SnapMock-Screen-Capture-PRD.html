Document Overview

Purpose

This document defines the functional requirements for the SnapMock Screen Capture feature. Screen Capture takes an image of the screen, a window, or a user-drawn region and hands that image to the Library, where it becomes a .smk file ready for annotation. The feature is the front door of the capture-to-library workflow defined in the Library PRD (Section 2.1): the user presses a key, draws a region, and the result appears in the Library without a file dialog.

Two terms are used throughout. A screen capture is the act of reading pixels from the display into an image. A capture backend is the platform-specific code that performs that read; the rest of the application never talks to a platform directly.

Scope

This PRD covers: the three capture modes (full screen, active window, region); the entry points that start a capture (global hotkeys, system tray, Main Toolbar button, Capture menu, command-line invocation); capture options (delay, cursor, sound, multi-monitor, high-DPI, clipboard); the region selection overlay; the capture backend abstraction and the four platform backends (Linux X11, Linux Wayland, macOS, Windows); the post-capture handoff to the Library; a Capture category in the Preferences dialog; permission onboarding on macOS and Wayland; data models; serialization; keyboard shortcuts; and acceptance criteria.

This document does not redefine the Library, the .smk format, or the Preferences dialog frame. Scrolling capture and freehand region capture are positioned in Section 2 but not specified.

Dependencies

  • Library PRD: capture-to-library workflow (Section 2.3, Section 6), auto-naming (Section 6.2), Library preferences (Section 8.1), library_metadata (Section 11.1).
  • Library Implementation Notes: the existing entry point MainWindow.add_to_library(image, source), the toast, the auto-open preference, and LibraryManager.create_from_image.
  • General UI PRD: menu bar (Section 3), Main Toolbar (Section 4), Preferences dialog (Section 11.3), keyboard shortcuts (Section 12), first-run experience (Section 16), and the never-disabled controls principle (Section 1.3).
  • Navigation & Raster Operations PRD: raster selection drawing conventions (Section 5.3) that the region overlay mirrors; clipboard image paste (Section 9.3.3).
  • Technical Architecture PRD: platform targets (Section 7.1), platform abstraction (Section 7.2), dependency policy (Section 9.1), .smk manifest (Section 3.8.1).

Capture Modes

Mode Summary

A capture mode names what part of the display is read. Every entry point in Section 3 starts a capture in one mode. The default mode is a preference (Section 8.1) and is Region on first run.

ModeIdentifierWhat is capturedOverlay shownVersion 1
Full Screenfull_screenOne monitor, or every monitor, per the Full Screen Scope preference.NoYes
Active Windowactive_windowThe window that had keyboard focus when the capture was triggered.NoYes, where the backend supports it
RegionregionA rectangle the user draws over a frozen image of the screen.YesYes
ScrollingscrollingA window's full content, stitched while it scrolls.YesDeferred (Section 2.5)
Freehand RegionfreehandA non-rectangular area the user draws.YesOut of scope (Section 2.6)

Full Screen

  • The capture manager (Section 6.1) asks the capture backend for a screen grab of every monitor, then keeps either the monitor under the mouse cursor or all monitors, per the Full Screen Scope preference (Section 4.4).
  • No overlay is shown. The delay timer (Section 4.1) applies before the grab.
  • The SnapMock window is hidden first when the Hide Window preference is on (Section 3.6).
  • The resulting image is handed to the Library (Section 7.1) with the capture mode recorded in capture_metadata (Section 12).

Active Window

  • The capture backend reports the geometry of the window that had focus at the moment the capture was triggered. When SnapMock itself had focus and Hide Window is on, the backend reports the window that had focus before SnapMock.
  • The screen grab is cropped to that geometry. Window decorations (title bar, borders) are included; a drop shadow is excluded where the platform reports the shadow extent separately.
  • Where the backend cannot report window geometry (Wayland in version 1), the mode degrades to Region with the message "Active window capture is not available on this desktop. Draw the region instead." shown in the overlay's hint bar (Section 5.2).
  • Windows that are minimized or on another virtual desktop are never captured; the message "No active window found" is shown and no file is created.

Region

  • The capture backend grabs every monitor first. The region selection overlay (Section 5) then shows that frozen image and lets the user draw a rectangle over it.
  • The frozen-image approach is deliberate. It works identically on every backend, it lets the overlay dim and magnify without reading the live screen, and it removes the race between the overlay appearing and the screen changing.
  • On confirmation the frozen image is cropped to the region in physical pixels (Section 4.5) and handed to the Library.
  • The region overlay is the only mode that shows the cursor image (Section 4.2) as a composited element, because the frozen image is taken before the overlay covers the screen.

Scrolling Capture

Scrolling capture is deferred to a later version. Reason: every platform requires a different stitching strategy (synthetic scroll events on X11 and Windows, accessibility APIs on macOS, nothing portable on Wayland), and the image stitching itself needs overlap detection that is a project of its own. The capture mode identifier scrolling is reserved so that the data model (Section 10) does not change when it arrives. A menu entry is not shown in version 1; an absent feature is not a disabled control.

Freehand Region

Freehand region capture is out of scope for this PRD. Reason: the Raster Selection (Freeform / Lasso) tool already produces a non-rectangular cut from any captured image inside the editor (Navigation & Raster Operations PRD, Section 6). Capturing a rectangle and lassoing inside it gives the same result with one interaction model instead of two.

Capture Entry Points

An entry point is any control or event that starts a capture. Every entry point builds a CaptureRequest (Section 10.2) and passes it to the capture manager. The manager, not the entry point, applies the delay, hides the window, and chooses the backend.

Global Hotkeys

A global hotkey is a key combination the operating system delivers to SnapMock while another application has focus. Global hotkeys are registered by a hotkey backend (Section 6.7) when the application starts and again whenever a hotkey preference changes.

ActionDefault keySetting key
Capture RegionPrintScreencapture/hotkeyRegion
Capture Active WindowAlt+PrintScreencapture/hotkeyWindow
Capture Full ScreenCtrl+PrintScreencapture/hotkeyFullScreen
  • Where they work: X11 and Windows register hotkeys in-process in version 1. Wayland and macOS do not; on those platforms the same three actions are reachable through the command-line invocation (Section 3.5) bound to a desktop shortcut, and the first-run page explains how (Section 9.2).
  • Registration failure: when the operating system refuses a key because another application owns it, the hotkey is recorded as unregistered, the Preferences dialog shows "In use by another application" beside it, and a toast says "PrintScreen is in use by another application. Change it in Preferences > Capture." The application keeps running.
  • Editing: each hotkey is edited in Preferences > Capture with a key sequence editor. Clearing the field removes the hotkey. Changes register immediately; the previous key is released first.
  • In-application use: the same key sequences are also ordinary application shortcuts (Section 13), so a user whose desktop swallows PrintScreen can still press it while SnapMock has focus, where the desktop allows it.
  • Trigger while a capture is in progress: ignored. One capture at a time.

Command-Line Invocation and Single Instance

The command-line invocation is the universal entry point. It exists so that desktops which do not allow in-process hotkey registration (Wayland, and macOS in version 1) can still bind a key to a capture.

  • Syntax: snapmock --capture <mode>, where <mode> is region, window, or full. snapmock --capture with no mode uses the default mode preference. Additional flags: --delay <seconds> overrides the delay for this capture only.
  • Single instance: on startup SnapMock connects to a single-instance channel, a local socket named for the current user. If a running instance answers, the new process forwards its command line to it and exits with status 0. If no instance answers, the new process becomes the running instance and listens on the channel.
  • No running instance: snapmock --capture <mode> starts the application, performs the capture as the first action after the main window exists, and then continues running as the editor. The main window stays hidden until the capture completes when Hide Window is on.
  • Forwarding delay: forwarding a request to a running instance completes within 100 milliseconds on a warm system. This is the number that makes the desktop-shortcut route feel like a native hotkey.
  • Channel failure: if the channel cannot be created (a stale socket from a crash), the stale endpoint is removed and creation is retried once. If it still fails, the application runs without a channel and logs the reason; a second launch then opens a second window, as it does today.

The SnapMock Window During Capture

The application's own window must not appear in a capture unless the user wants it to. The Hide Window preference (Section 8.1), on by default, governs this.

  • Hide Window on: before the screen grab, the capture manager records the main window state (geometry, maximized or full-screen flag, active tab) and hides every SnapMock top-level window, including floating panels and the toast. It then waits until the platform confirms the window is gone, or 250 milliseconds, whichever is first, and then grabs the screen. Two compositor frames are the usual wait.
  • Hide Window off: the window stays where it is and is captured like any other window. This is the mode for capturing SnapMock itself.
  • Minimize is not used. Minimizing animates on several desktops and leaves a taskbar transition in the grab. Hiding does not.
  • Restore: after the capture completes, is cancelled, or fails, every hidden window is shown again in its recorded state, and the main window is raised and activated. Restore happens exactly once, from a single code path, so no failure mode leaves the window hidden. If the application is quit while hidden, the recorded geometry is what is saved to settings.
  • Modal dialogs: when a modal dialog (Preferences, Export, an unsaved-changes prompt) is open, a capture request is refused with the message "Close the open dialog before capturing." shown in that dialog's parent window and, if the request came from the tray or command line, as a system notification.
  • Delay interaction: with a delay set, the window hides at the end of the countdown, not the start, so the user can keep working in SnapMock until the grab.

Capture Options

Delay Timer

  • The delay is the number of seconds between the trigger and the screen grab. Range 0 to 60, default 0. Set in Preferences, the Capture menu, the tray menu, the toolbar button menu, or --delay on the command line.
  • During a countdown a small frameless countdown badge shows the remaining seconds. It is placed at the top center of the monitor under the mouse cursor where the platform allows placement, and wherever the compositor puts it otherwise. The badge is excluded from the capture by hiding it 100 milliseconds before the grab.
  • The tray icon tooltip mirrors the countdown (Section 3.2).
  • Escape while the badge has focus, or clicking the badge, cancels the countdown. A cancelled countdown restores nothing, because nothing was hidden yet.
  • A second trigger during a countdown is ignored.

Mouse Cursor

  • The Include Cursor preference, off by default, composites the mouse cursor image into the captured image at its position at grab time.
  • The capture backend supplies the cursor image and hotspot when the platform exposes them (Section 6). When it does not, the option has no effect and the Preferences dialog shows "Not available on this desktop" beside the checkbox.
  • In Region mode the cursor is composited into the frozen image before the overlay appears, so what the user sees in the overlay is what is captured.
  • The cursor is drawn at the monitor's device pixel ratio so it is not blurred on high-DPI displays.

Capture Sound

  • The Play Sound preference, off by default, plays a short shutter sound when the grab completes. The sound file ships in resources/sounds/ and is played through Qt's sound effect class, which ships with PyQt6.
  • The sound plays after the grab, never before it, so it cannot appear in a recording of the screen taken at the same moment.
  • If audio output is unavailable the failure is silent. Sound is never a reason for a capture to fail.

Multi-Monitor Behavior

  • Monitor model: the capture backend reports every monitor as a MonitorInfo (Section 10.4) with logical geometry, physical geometry, device pixel ratio, and a primary flag. The union of the logical geometries is the virtual desktop.
  • Full Screen Scope preference: Monitor Under Cursor (default) captures the monitor containing the mouse cursor at grab time. All Monitors captures the whole virtual desktop as one image; gaps between monitors of different sizes are filled with black.
  • Active Window: the window is captured from the monitor that holds most of its area. A window spanning two monitors is captured across both.
  • Region: the overlay covers every monitor (Section 5.7). A region may span two monitors only when they share a device pixel ratio; otherwise the region is clamped to the monitor where the drag began.
  • Monitor change during capture: if a monitor is connected or removed between the grab and the confirmation, the capture proceeds from the frozen image. Nothing is re-read from the screen.

High-DPI Scaling

Two coordinate systems exist on a scaled display. Logical pixels are the units Qt uses for widget geometry. Physical pixels are the units of the display hardware. The device pixel ratio is physical divided by logical, for example 2.0 on a 200 percent display.

  • Captures are always taken in physical pixels. The canvas of the resulting .smk file has the physical dimensions, so a 200 percent display produces a canvas twice the logical size. Nothing is downscaled.
  • The overlay draws in logical pixels and converts the drawn rectangle to physical pixels at confirmation, rounding outward so no edge pixel is lost.
  • The device pixel ratio of the source monitor is stored in capture_metadata (Section 12) so a later version can offer a scaled export.
  • Mixed ratios across monitors are supported: each monitor's grab is stored at its own ratio, and All Monitors composites them at the highest ratio present.

Clipboard Copy

  • The Copy to Clipboard preference, off by default, places the captured image on the system clipboard as a PNG at the same time it is handed to the Library.
  • Library storage always happens. Clipboard copy is in addition, never instead.
  • With this preference on, a capture can be pasted into the active non-library document with Ctrl+V (Navigation & Raster Operations PRD, Section 9.3.3). That is the supported way to bring a capture into an existing mockup.

Region Selection Overlay

Overlay Model

The region selection overlay is a set of full-screen, frameless, always-on-top windows, one per monitor, created inside the editor process. Each window paints the frozen image of its monitor and the selection graphics on top. The overlay owns keyboard focus while it is visible and releases it on confirm or cancel.

  • The overlay is created lazily on the first region capture and reused afterward, so the second capture is faster than the first.
  • The overlay reads the current preferences at the moment it is shown. It does not watch for changes while visible.
  • The overlay never reads the live screen. Everything it shows comes from the frozen image and from the MonitorInfo list.
  • Overlay code lives in snapmock/capture/overlay.py and depends on nothing in the editor except the theme colors. It is the one piece of this feature that runs while the main window is hidden, so it must not touch the main window.

Appearance

  • Dimming: the frozen image is covered with 40 percent black. Inside the selected rectangle the image shows undimmed.
  • Crosshair: before a drag begins, a full-height vertical and full-width horizontal 1 px line in the accent color follow the cursor. The crosshair hides during the drag and returns after release if the drag was discarded.
  • Selection border: a 1 px solid line in the accent color with a 1 px white inner line, so it reads on light and dark content.
  • Dimensions label: "W × H" in physical pixels, drawn in a small dark pill just outside the rectangle's bottom-right corner, flipping to the inside when there is no room.
  • Hint bar: a single line at the top center of the monitor under the cursor: "Drag to select a region. Shift: square. Alt: from center. Space: move. Enter: capture. Esc: cancel." When Active Window degraded to Region (Section 2.3), the degradation message is shown first for 3 seconds.
  • Cursor: crosshair while idle and dragging; closed hand while Space-moving.
  • Theme: colors come from the ThemeManager (General UI PRD, Section 13.4) so the overlay matches the active theme.

Mouse Interaction

  • Press and drag with the left button draws the rectangle from the press point to the current point. Dimensions update live.
  • Release with a rectangle of at least 4 by 4 logical pixels confirms the capture immediately. Snagit users expect release to capture; there is no separate adjustment step in version 1.
  • Release with a smaller rectangle discards the drag and returns to the idle crosshair. A plain click therefore does nothing destructive.
  • Space held during a drag moves the whole rectangle with the mouse instead of resizing it. Releasing Space resumes resizing from the new position.
  • Right-click cancels the overlay at any time, the same as Escape.
  • Mouse wheel is ignored. There is no zoom in the overlay; the magnifier (Section 5.5) covers precision.
  • Auto edge scroll does not apply; the overlay already shows every pixel of every monitor.

Magnifier and Dimensions Label

  • The magnifier is a 132 by 132 logical pixel square showing an 11 by 11 physical pixel neighborhood of the cursor at 12 times enlargement, with a 1 px grid and the center pixel outlined in the accent color.
  • Below the image the magnifier shows the cursor position in physical pixels, "X: 1234 Y: 567", and the hex color of the center pixel.
  • The magnifier sits 20 logical pixels below and to the right of the cursor and flips to the opposite side when it would leave the monitor.
  • The magnifier is visible while idle and while dragging. It hides while Space-moving, because the cursor is then not on an edge.
  • The Show Magnifier preference (Section 8.1), on by default, turns it off for users who find it distracting.

Cancel and Escape

  • Escape, right-click, or the overlay losing focus to another application cancels the capture. The overlay hides, the SnapMock windows are restored (Section 3.6), and no file is created.
  • A cancelled capture shows no toast. Cancel is silent.
  • Focus loss is treated as cancel because an overlay left on screen after an alt-tab is a trap.

Behavior Across Monitors

  • One overlay window per monitor, each showing that monitor's frozen image. The crosshair and magnifier appear on the monitor under the cursor.
  • A drag that crosses into a second monitor with the same device pixel ratio continues, and the rectangle spans both. The dimming and border are drawn consistently in each window from a shared selection model.
  • A drag that crosses into a monitor with a different device pixel ratio is clamped at the edge of the monitor where it began. The hint bar says "Selection cannot cross monitors with different scaling."
  • On Wayland the compositor decides where windows go. Each overlay window asks for full-screen on its own monitor through Qt's screen assignment. If the compositor places two overlays on one monitor, the capture still works from the frozen image; only the visual is wrong. This is recorded as a known limitation in Section 6.8.

Platform Backends

The Capture Backend Abstraction

The application code sees exactly one interface, CaptureBackend, and one coordinator, CaptureManager. Nothing outside snapmock/capture/ imports a platform module.

CaptureBackend methodReturnsDescription
capabilities()BackendCapabilitiesWhich modes and options this backend supports on this session (Section 10.6). Called once at startup and shown in Preferences.
monitors()list[MonitorInfo]Every connected monitor with logical and physical geometry and device pixel ratio.
grab_screens(include_cursor)ScreenGrabOne image per monitor in physical pixels, plus the cursor image and hotspot when requested and available. Raises CaptureError with a user-readable reason on failure.
active_window_geometry()QRect | NoneLogical geometry of the focused window, excluding shadow, or None when the platform cannot say.
request_permission()PermissionStateGranted, Denied, or NotRequired. Triggers the platform prompt where one exists (macOS). Never blocks for longer than the platform prompt itself.

CaptureManager owns one CaptureBackend, one HotkeyBackend (Section 6.7), the overlay, the delay timer, and the single-instance channel. It exposes start(request), cancel(), and the signals capture_completed(CaptureResult) and capture_failed(reason). MainWindow connects capture_completed to add_to_library and capture_failed to a message. That is the whole contract between capture and the editor.

Backend Selection

  • Selection happens once at startup in snapmock/capture/__init__.py from the platform name and, on Linux, the session type.
  • Linux with a Wayland session (the Qt platform name is wayland, or the session environment reports Wayland) selects the Wayland portal backend. Linux otherwise selects the X11 backend. macOS selects the macOS backend. Windows selects the Windows backend.
  • An unrecognized platform selects a null backend whose capabilities() reports nothing supported. Every capture entry point then shows "Screen capture is not supported on this platform."
  • Selection is not user-configurable. A wrong backend produces black images, which is worse than no backend.

Linux Wayland

Under Wayland an application cannot read pixels that belong to other applications. The desktop portal is the D-Bus service that a compositor exposes to grant privileged operations to applications. SnapMock uses its Screenshot interface and nothing else.

Post-Capture Flow

Handoff to the Library

  • On capture_completed, MainWindow calls the existing entry point add_to_library(image, source="capture"). The Library creates the .smk file in the current library folder, names it with the auto-naming convention (Library PRD, Section 6.2), and refreshes the panel. None of that changes.
  • The entry point gains one optional keyword argument, capture_metadata, carrying the CaptureMetadata record (Section 10.5). LibraryManager.create_from_image passes it through to the manifest (Section 12). Callers that omit it, such as drag-and-drop import, are unaffected.
  • The image handed over is the final cropped image in physical pixels. The Library does not know or care which mode produced it.
  • The handoff runs on the main thread after the overlay has hidden and before the SnapMock windows are restored, so the new tab exists when the window reappears.

Auto-Open and Toast

  • Auto-open captures (Library PRD, Section 8.1) governs whether the new file opens in a tab. Screen Capture adds no preference of its own for this.
  • Toast notifications (Library PRD, Section 8.1) governs the "Captured to Library: [filename]" toast with its Open link. Screen Capture adds no preference of its own for this.
  • When Copy to Clipboard is on, the toast text is "Captured to Library and clipboard: [filename]".
  • When the main window is hidden in the tray (Keep Running in Tray on) at capture time, the toast has no window to appear in. A system notification with the same text is shown instead, through the tray icon's message facility. Clicking it shows the main window with the new tab active.

Capture While a Non-Library Document Is Active

Nothing changes. A capture always creates a library file. If Auto-open is on, the new library tab opens and becomes active; the non-library document keeps its tab, its dirty state, and its undo stack, and is not saved or prompted. If Auto-open is off, the non-library document remains active and the toast offers the Open link.

The alternative, placing the capture into the active document as a raster item, was considered and rejected for version 1. It would make the same key do two different things depending on which tab is active, and the clipboard route (Section 4.6) already covers the need.

Capture Failure

  • capture_failed(reason) carries a user-readable sentence from the backend. MainWindow shows it as a toast when the window is visible and as a system notification otherwise. No file is created.
  • The SnapMock windows are restored on failure exactly as on success (Section 3.6).
  • Failures are also written to the application log with the platform, backend, mode, and the underlying error text, so a bug report has what it needs.
  • A failure inside the overlay (an exception while painting or handling input) is caught at the overlay boundary, reported as a failure with reason "The capture overlay encountered an error", and the overlay is destroyed so the next capture creates a fresh one. The editor keeps running.

First-Run and Permission Onboarding

Onboarding runs the first time a capture is attempted on a platform that needs setup, not at application start. A user who never captures never sees it. Each onboarding dialog has a "Don't show this again" checkbox stored under capture/onboardingShown.

macOS Screen Recording Permission

  • On the first capture request, request_permission() runs the preflight check. If permission is granted, capture proceeds and no dialog is shown.
  • If not granted, an onboarding dialog explains: "macOS asks you to allow SnapMock to record the screen before it can take screenshots. Click Continue to see the system prompt. If you have already denied it, open System Settings and enable SnapMock under Privacy & Security > Screen Recording." Buttons: Continue, Open System Settings, Cancel.
  • Continue calls the system request, which shows Apple's dialog once. Open System Settings opens the Screen Recording pane directly.
  • After the user grants permission, macOS does not apply it to the running process. The dialog's final state says "Quit and reopen SnapMock to finish." with a Quit button.
  • Until permission is granted, every capture fails with the Section 6.5 message, and the Preferences capability line reads "Screen Recording permission: not granted".

Wayland Portal and Desktop Shortcut

  • On the first capture request under Wayland, an onboarding dialog explains two things in two short panels.
  • Panel one, consent: "Your desktop will ask whether SnapMock may take a screenshot. This is the desktop's own dialog. Some desktops ask once; some ask every time."
  • Panel two, hotkey: "Wayland desktops do not let applications register their own keyboard shortcuts. To capture with PrintScreen, bind a shortcut in your desktop's keyboard settings to this command:" followed by snapmock --capture region in a copyable field, a Copy button, and one line each for the window and full-screen commands. Below that, one sentence per known desktop: where the keyboard shortcut settings are on GNOME and on KDE, and that the desktop's own PrintScreen binding must be removed or changed first.
  • Buttons: Continue (proceeds to the capture), Cancel.
  • The same content is reachable at any time from Preferences > Capture through a "How to set up a desktop shortcut..." link, so the dialog is not the only place it lives.

Hotkey Conflicts

  • On X11 and Windows, a failed registration at startup shows one toast: "PrintScreen is in use by another application. Change it in Preferences > Capture." The toast names the specific key that failed. Multiple failures are collected into one toast.
  • Known conflicts are documented in the Preferences help text: GNOME on X11 and Windows 11 with the Snipping Tool shortcut both claim PrintScreen by default.
  • Changing a hotkey to one that is in use fails immediately in the key sequence editor with the same message, and the previous key stays registered.

Command Definitions

Screen Capture introduces no undoable commands. A capture creates a file in the Library; it does not mutate any open scene, so it never touches a CommandStack. The Library's own file operations (rename, move, folder creation) remain the commands defined in the Library PRD, Section 10.

Two rules follow from this. First, undo after a capture undoes the last action in the active document, not the capture; the file is removed through the Library panel's Delete like any other file. Second, the auto-opened tab starts with an empty undo stack, exactly as a file opened from the panel does, because the capture is the file's origin, not an edit to it.

If a later version adds "capture into the active document" (rejected for version 1 in Section 7.3), it would be an AddItemCommand on that document and would be specified then.

Settings

All settings listed in Section 8.1 are stored through AppSettings under the capture/ prefix, plus capture/onboardingShown (boolean) and capture/lastMode (string, the mode of the most recent capture, for the toolbar tooltip). Session Persistence

  • Tray visibility and the Keep Running in Tray state are preferences, not session state.
  • When the application quits while the main window is hidden in the tray, the window geometry saved is the geometry recorded before hiding, not the hidden state.
  • No capture-in-progress state is persisted. A crash during capture leaves nothing to recover; the next launch starts idle.

Acceptance Criteria

Capture Modes

  1. A full-screen capture with scope Monitor Under Cursor produces an image whose size equals the physical size of the monitor containing the cursor.
  2. A full-screen capture with scope All Monitors produces one image covering the virtual desktop, with black where no monitor exists.
  3. An active-window capture on X11, macOS, and Windows produces an image whose size equals the window's frame size, excluding shadow.
  4. An active-window request on Wayland opens the region overlay and shows the degradation message in the hint bar.
  5. A region capture produces an image whose size equals the drawn rectangle in physical pixels.
  6. No menu, tray, or toolbar entry for scrolling or freehand capture exists in version 1.

Entry Points

  1. On X11 and Windows, pressing the default hotkey while another application has focus starts the corresponding capture.
  2. A hotkey that fails to register produces exactly one toast naming the key, and the application continues.
  3. Changing a hotkey in Preferences releases the old key and registers the new one without restart.
  4. The tray icon appears when the preference is on and the platform has a tray; each tray menu item performs its action.
  5. With Keep Running in Tray on, closing the main window hides it and hotkeys continue to work; Show SnapMock restores it.
  6. The Main Toolbar Capture button's main click uses the default mode; its arrow menu offers all three modes.
  7. The Capture menu appears after Library and before Help with every item from Section 3.4, and its shortcut labels follow the hotkey preferences.
  8. snapmock --capture region with a running instance forwards the request within 100 milliseconds and exits with status 0; the running instance shows the overlay.
  9. snapmock --capture full with no running instance starts the application, captures, and leaves the editor running.
  10. With Hide Window on, no SnapMock window appears in any capture; with it off, the SnapMock window is captured.
  11. After every capture outcome (success, cancel, failure) the main window is restored to its recorded geometry and state and is active.
  12. A capture request while a modal dialog is open is refused with the specified message and creates no file.

Capture Options

  1. With a delay of N seconds, the grab occurs N seconds (plus or minus 100 milliseconds) after the trigger, and the countdown badge shows the remaining seconds and does not appear in the capture.
  2. Escape during a countdown cancels it and creates no file.
  3. With Include Cursor on, on X11, macOS, and Windows, the cursor appears in the capture at its grab-time position; on Wayland the preference shows the unavailable message.
  4. With Play Sound on, the shutter sound plays once per completed capture and never on cancel or failure.
  5. On a display at 200 percent scaling, a region drawn at 400 by 300 logical pixels produces an 800 by 600 pixel image.
  6. With Copy to Clipboard on, the system clipboard holds a PNG of the capture after the capture, and the library file is also created.
  7. A region spanning two monitors with equal device pixel ratios is captured across both; with unequal ratios the region is clamped to the first monitor and the hint bar explains.

Region Selection Overlay

  1. The overlay covers every monitor and shows the frozen image, dimmed 40 percent, with the crosshair and magnifier following the cursor.
  2. Dragging draws the rectangle with a live "W × H" label; release with at least 4 by 4 logical pixels captures immediately.
  3. Release with a smaller rectangle discards the drag and leaves the overlay open.
  4. Shift constrains to a square; Alt draws from the center; Shift+Alt does both; Space during a drag moves the rectangle.
  5. The magnifier shows the 11 by 11 pixel neighborhood, the physical cursor coordinates, and the center pixel's hex color, and flips sides near monitor edges.
  6. Escape, right-click, and focus loss to another application each cancel the overlay silently and restore the SnapMock windows.
  7. The overlay renders the crosshair and rectangle at 60 frames per second on a 4K monitor.
  8. An exception inside the overlay is reported as a capture failure; the editor keeps running and the next capture works.

Platform Backends

  1. No module outside snapmock/capture/ imports a platform-specific module or calls ctypes.
  2. The backend selected on a Wayland session is the portal backend; on an X11 session it is the X11 backend; the selection is logged at startup.
  3. On Wayland with the portal absent, every capture fails with the Section 6.4 message and no X11 grab is attempted.
  4. On macOS without Screen Recording permission, the onboarding dialog appears on the first capture request and the Open System Settings button opens the Screen Recording pane.
  5. On Windows, an active-window capture excludes the invisible resize border.
  6. The Preferences capability line reports the backend name and each unavailable capability.
  7. The test suite runs every backend-independent path (manager, overlay, models, single instance, preferences) against a fake backend on the offscreen platform.

Post-Capture Flow

  1. Every successful capture calls add_to_library once with source "capture" and a CaptureMetadata record, and the file appears in the Library panel immediately.
  2. With Auto-open on, the new file opens in a tab and becomes active; with it off, it does not open and the toast's Open link opens it.
  3. The toast text, and the system notification when the window is hidden, match Section 7.2.
  4. A capture taken while a dirty non-library document is active leaves that document's tab, dirty flag, and undo stack unchanged.
  5. A failed capture shows the backend's reason, creates no file, and restores the windows.

Preferences and Onboarding

  1. The Capture category appears after Library with every setting from Section 8.1, and every change applies immediately and persists across sessions.
  2. The hotkey editors are replaced by command-line guidance with a working Copy button on Wayland and macOS.
  3. Each onboarding dialog appears on the first capture request only, honors Don't show this again, and is reachable again from Preferences.

Serialization

  1. A captured file's manifest.json contains capture_metadata with every field from Section 12.1, and library_metadata.captured_at equals the grab time.
  2. A file without capture_metadata loads and displays without error.
  3. Settings written on Linux with a PrintScreen hotkey load on Windows with the same key.

Open Questions

These items do not change a requirement. Each needs an answer before the section it names is implemented; the implementation kickoff prompt carries them forward.

Open — GNOME consent dialog frequency (Section 6.4)

Whether the GNOME portal asks once per session or on every screenshot call is inferred, not checked. If it asks every time, the Wayland experience is one click worse than Section 6.4 implies. The onboarding text in Section 9.2 already warns of both cases.

Open — macOS active window through ctypes (Section 6.5)

The Core Graphics window list is reachable from ctypes, but pyobjc is the safer route. Section 6.5 names pyobjc as an optional implementation candidate; the implementer should decide after a spike.

Open — Wayland overlay placement (Section 5.7)

Compositors may ignore the per-monitor full-screen request. Section 5.7 records this as a known limitation. If it bites on GNOME in practice, a single overlay window spanning the virtual desktop is the fallback to evaluate.

Open — Windows 11 PrintScreen (Section 9.3)

Windows 11 can bind PrintScreen to the Snipping Tool by default. Section 9.3 documents the conflict. Whether SnapMock should offer to take over the key on first run is a version 1.1 question.

Open — Sound asset (Section 4.3)

The shutter sound file needs a license-compatible source before it ships.
