## Starting state, verified at commit 13d0054 on 09-13-26

Verified by running the code on this machine (an Intel i7-11700K, sixteen threads, the offscreen platform, no other run sharing the machine), not by reading it. Three probes, each of which Phase 1 turns into a measurement the notes carry:

- **The fit on release misses 9.10's 50 ms at 5000 points at every smoothing, and at 0 percent from about 500 jittery points.** `FreehandItem.smooth` over a sine-wave stroke: with no jitter, 6.5 ms at 500 points, 41 ms at 2000, and **127 to 159 ms at 5000** whatever the smoothing. With a pixel of jitter on every point, 4 to 7 ms at 500 points and 140 ms at 5000 for smoothing 50 and 100 percent — but at **0 percent smoothing 111 ms at 500 points, 473 ms at 2000, and 1304 ms at 5000**, producing 238, 993, and 2475 segments. The Basic Shape remainder notes measured 65 to 70 ms at 50 and 100 percent and up to 630 ms at 0 percent on 09-11-26 with a different stroke; the shape of the result is the same. Two costs are visible in the code without profiling: `simplify_rdp` is a Python loop over every point of every span, and at 0 percent the 0.5 px floor on the fit error sits below a pixel of jitter, so the fit splits until nearly every point is a segment end, running the twenty-iteration reparameterization on each near miss.
- **The live preview's paint grows with the stroke and passes a frame at 5000 points.** `FreehandItem.paint` of the quadratic preview, antialiased, onto a 2800 by 400 pixel image: **1.8 ms at 500 points, 11.2 ms at 2000, 26.5 ms at 5000**, against the 16.7 ms a frame at 60 frames a second allows. `add_point` itself is cheap, 0.004 to 0.014 ms per point at any length, so the cost is the painting of the whole path on every move, which is what 9.10's 500-point rule addresses. Nothing in `FreehandItem` or the tool limits the painted path while a stroke is drawn.
- **The cursor is the crosshair throughout.** `FreehandTool.cursor` returns `Qt.CursorShape.CrossCursor`, and nothing changes it on the press. The Blur tool's `cursor` property returns `brush_cursor(round(self.brush_size * zoom))` and `_refresh_cursor` re-applies it when the size or the zoom changes; the Highlighter returns `marker_tip_cursor()`.

## Decisions to surface

Apply the two-part test from the global guidance. Three decisions are expected to pass it; present all three with the consequential decision template before Phase 2 and wait.

- **1. What the brush-tip cursor is, and when it shows.** 9.2 asks that on the mouse press the cursor become a filled circle, `stroke_width` across, in `stroke_color`; General UI PRD 6.6 gives every drawing tool the crosshair and already carries a row each for the Blur tool's brush ring and the Highlighter's marker tip. The example: a 2 px red stroke at 100 percent zoom, where a filled circle 2 px across is a dot the eye cannot find on a screenshot, and a 30 px stroke at 400 percent zoom, where the same rule gives a 120 px disc. Option A, 9.2 as written with two guards from the Blur brush — a minimum size below which the circle is drawn at the minimum with a halo, and `BRUSH_CURSOR_MAX` above — scaled by the zoom as the brush cursor is, filled with the stroke colour at the stroke opacity over the halo ring, and shown from the press to the release only, the crosshair before and after. Option B, the same cursor shown whenever the tool is active, as the Blur brush and the marker tip are, so the user sees the stroke's width and colour before pressing, which is the reason a brush tip exists; a departure from 9.2's "on the mouse press" in the wording only. Option C, keep the crosshair and record 9.2's cursor as a departure with a row, since the Basic Shape remainder work already left it and no display run has asked for it. Why it matters: it is the last piece of Section 9 a user can see, it is on screen for every stroke, and a cursor that changes on the press and back on the release flickers where one that stays does not. The cost of B: 6.6 gains a row that reads differently from 9.2 and both documents carry it; a hidden cursor while the pointer sits still over the canvas is a dot in the stroke's colour, which could be mistaken for a mark. Recommendation: B, with the crosshair's hotspot rule (the circle's centre) and the halo ring so the disc reads on any content; it is what the Blur brush already does and what a user of a drawing program expects. Follow-on detail: `preview_cursor` and `brush_cursor` in `ui/cursors.py` are the two shapes to build from; the cursor is keyed by size and colour in the cache; `_refresh_cursor` runs on `stroke_width`, `stroke_color`, and `stroke_opacity` changes and on `zoom_changed`, as the Blur tool's does on `brush_size`.
- **2. How the 50 ms fit is met, and what 0 percent smoothing means for a jittery stroke.** 9.10 asks for the fit inside 50 ms at 5000 raw points; the measurement gives 127 to 159 ms for a smooth stroke and 1304 ms at 0 percent for a jittery one. The example: a slow circle drawn around a paragraph with a shaky hand, 5000 points, at the slider's default of 50 percent — 140 ms today, a visible pause before the snap 9.3 describes — and the same circle at 0 percent, over a second. Option A, make the pipeline faster without changing its result: `simplify_rdp` vectorised over each span with NumPy (it is the Python loop that dominates a smooth 5000-point stroke), the fit's per-piece arrays reused rather than rebuilt, and the reparameterization bounded; the result is pixel-identical wherever the arithmetic is the same, and every existing test stands. Option B, A plus a floor at 0 percent that rises with the stroke's own noise — the fit error never below the stroke's median point-to-point deviation — so a jittery stroke at 0 percent produces tens of segments rather than thousands; 9.3 says 0 percent "closely follows the original points, giving a nearly raw path", and a segment per point is not nearly raw, it is raw, but the row is a departure from the 0.5 px floor the remainder work recorded. Option C, run the fit on a background thread and show the raw preview until it lands, which is the first thread in the code and the option the Blur performance work rejected for the same reason. Option D, A alone, and record whatever 0 percent measures as a departure with the figure. Why it matters: every stroke pays this on release, and the default smoothing is the case that must be fast; whether 0 percent may change the result decides whether a user's saved strokes re-fit differently on load. The cost of B: a stroke saved at 0 percent before this work fits to different segments when re-smoothed (never on load — the file carries its segments), and the notes must say so. Recommendation: A first and measured, then B only if A leaves 0 percent over the budget at 5000 jittery points — decided in Phase 3 on the profile, not now — with the choice recorded in the row either way. Follow-on detail: the existing tests in `tests/test_freehand_pipeline.py` and the point-editing tests pin the fit's result on their strokes and must pass unchanged under A; a departure row for B names the strokes on which the result differs.
- **3. How the live preview holds 60 frames a second past 2000 points.** 9.10 says to render only the most recent 500 points while drawing and the full path on release. The example: a long looping underline across a wide screenshot, 5000 points, whose first four-fifths would vanish from the screen at 2000 points under the rule as written and come back on release. Option A, the rule as written: past 2000 points the item paints the last 500 points' path only, and the whole path on release — cheapest, and the one the PRD names, but the start of a long stroke disappears while the user is still drawing it. Option B, the same budget met without anything vanishing: the older part of the preview is frozen into a cached image at the view's scale each time the tail passes 500 points, and each frame paints the cache and the live tail only, so the paint cost is bounded by the tail; on release the cache is dropped and the full path painted. Option C, record the 26.5 ms at 5000 points as a departure: it is over a frame only past about 3000 points on this machine, and the antialiased paint of one 5000-point path is what any drawing program pays. Why it matters: it is the difference between a stroke the user can see all of while drawing and one that disappears behind them, and the frame budget is spent on every move of the longest strokes, which are the ones drawn slowly and carefully. The cost of B: a cached image that must follow the zoom (a zoom during a drag is not possible today, since the wheel is Ctrl+scroll and the drag consumes the mouse, but a resize or a scroll from auto-scroll at the viewport's edge is), the Shift segments' `restore_preview` must invalidate the cache when the snapshot it restores predates it, and the item's appearance during the drag is a raster copy of what was a vector path, which at 100 percent zoom is identical and at other zooms is scaled. Recommendation: B, since a stroke that vanishes while it is drawn is the kind of thing a display run would flag as a fault; A is the fallback if B's cache proves fragile under the Shift segments. Follow-on detail: the cache lives in `FreehandItem` beside `_preview`, keyed by the point count it covers; the tail's path starts at the last frozen point; `preview_snapshot` and `restore_preview` carry the cache's point count so a restore to a shorter stroke drops it.

Everything else follows the PRDs; where they are silent or disagree, decide, note it under the notes' decisions section and the PRD rows, and continue. Silences known now:

- The cursor's minimum drawn size, the same as the Blur brush's 4 px, and its ceiling, `BRUSH_CURSOR_MAX`; a stroke width past the ceiling draws at the ceiling.
- The cursor's fill is the stroke colour at the stroke opacity, over a white halo ring with a black outline, so a light colour on a light screenshot still reads; the hotspot is the centre.
- A locked or hidden layer does not change the cursor: General UI PRD 6.6's forbidden row names a locked item, not a locked layer, as the shared drawing notes' Section 2.3 recorded, and the press guard's message says what is wrong.
- The measurements are taken on the offscreen platform with a scratch script the notes describe, on a sine-wave stroke with and without a pixel of jitter, at 500, 2000, and 5000 points, with the machine named; a test holds a loose ceiling (one frame per move for the preview; 50 ms times a factor the notes justify for the fit) and never the measured figure itself.
- The 500-point tail and the 2000-point threshold of 9.10 are the values used, as module constants beside `MIN_STROKE_EXTENT`.
- 9.10's "raw point capture must not drop events" is met by the existing event route and is not changed; the notes say so.
- Pressure data stays null and is not this work's; the row says so once.
